## What was done

`services/worker/tasks.py` (613 lines, four task domains in one module) became the
`services.worker.tasks` package, one submodule per Celery wire-name namespace:

| Submodule | Wire names | Contents |
|---|---|---|
| `collection.py` | `collection.backfill_field`, `collection.collect_pass`, `collection.forward_fill_field`, `collection.scan_and_enqueue` | The 4 task wrappers, the injectable orchestrators (`run_collection`, `prepare_and_run`, `plan_backfill_scenes`, `collect_pass`, `due_field_ids`), the private runners, and the shared helpers (`CORE_INDICES`, `CollectionSummary`, `_summary_dict`, `field_to_aoi`, `_start_of_day`), all of which turned out to be collection-only |
| `interpret.py` | `interpret.field_pass` | `_interpret_for_pass` + wrapper |
| `sync.py` | `sync.publish_farm` | `_publish_farm` + wrapper |
| `analysis.py` | `analysis.analyse_aoi` | `_analyse_aoi` + wrapper (no DB at all) |

Naming decision: submodules are named after the **wire namespaces**, not the sibling worker
modules, because the task name is the externally visible contract. This intentionally mirrors
sibling names (`worker/collection.py` is the lock-gated collection engine,
`worker/tasks/collection.py` is its Celery orchestration; same for `interpret`). Python 3
absolute imports make the same-name siblings unambiguous; the layering reads as one domain,
two layers.

## The Celery findings (this split's whole risk surface)

- **The item-1 caveat was defused by the codebase itself**: every `@celery.task` carries an
  explicit `name=`, so registered wire names never depended on the module path. Nothing queued,
  scheduled, or beat-referenced can break from a move. The beat schedule references
  `"collection.scan_and_enqueue"` by string name.
- **Registration mechanics**: `celery_app.py` calls `autodiscover_tasks(["services.worker"])`,
  which imports the module named `tasks` in that package. With `tasks` as a package, that import
  runs `__init__.py`, whose re-export imports pull every submodule, which runs every decorator.
  Verified explicitly after the split:

  ```
  python -c "from services.worker.celery_app import celery; import services.worker.tasks; \
  print(sorted(n for n in celery.tasks if not n.startswith('celery.')))"
  ```

  gives the seven wire names plus `heartbeat` (which lives in `celery_app.py`, untouched).
- **Monkeypatching survives the split for a structural reason worth remembering**: tests do
  `import services.worker.tasks as tasks` then `monkeypatch.setattr(tasks.backfill_field,
  "delay", ...)`. That patches an attribute **on the task object**, and Celery task objects are
  app-registered singletons, so every importer (the workspace endpoint's function-local
  `from services.worker.tasks import backfill_field` included) sees the same object and the same
  patch. If the tests had instead patched the **module attribute**
  (`monkeypatch.setattr(tasks, "backfill_field", fake)`), the split would have silently broken
  them: code inside the submodule resolves names from its own module globals, not from the
  package `__init__`. Check which of the two patterns the tests use before any module split;
  only the object-attribute pattern is move-proof.
- **No cross-domain calls**: `_fan_out_backfill` enqueues `collect_pass_task.delay(...)` and
  `_scan_and_enqueue` enqueues `backfill_field` / `forward_fill_field`, all within the
  collection module, so no submodule imports another. `__init__` is the only join point.

## Lesson repeated from item 1 (apply it in the next splitter, not after)

The one ruff finding was again I001 on the module whose slice begins with a comment-attached
statement (`# The core indices...` + `CORE_INDICES = ...`): ruff isort wants exactly **one**
blank line between the import block and a following comment, while plain `def`/`class` starts
get two. The splitter joins header and body with two blank lines, so any module whose body
starts with a comment will need `ruff check --fix` once, or join that one with a single blank
line in the script. Item 3 should bake this in.
