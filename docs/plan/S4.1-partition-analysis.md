# S4.1 - Partition and index the analysis table

Date: 2026-06-12. Slice: backlog 0001 S4.1 (PRD 0001 R15/R18). Status: DONE.

## Why this shape

R16 fixes the scale problem: data volume, not request concurrency. Hundreds of thousands of
farms, each field accruing roughly 6 passes a month across several indices, and analysis rows
are never deleted (S4.3 prunes only the COG raster, the stats/provenance rows are forever).
At the R16 target that is millions of rows a month, all funneling into one table whose every
index keeps growing. Partitioning by time caps the working set: each month is a small,
separately-indexed table; old months go cold; date-bounded queries prune to the partitions
they touch.

- **Partition key: `pass_date`, monthly RANGE.** Every consumer either pins `field_id` (pruning
  harmless) or bounds time (analytics windows, as-of resolution, retention cutoff: pruning
  wins). Monthly because yearly partitions at target scale would still hold ~80M rows; at
  ~6-7M rows a month, a month is the right-sized unit. Partition count grows 12/year forever,
  which Postgres 16 handles comfortably.
- **Key widening is forced, not chosen.** Postgres requires the partition key inside the
  primary key and every unique constraint. PK becomes `(id, pass_date)`; `uq_analysis_identity`
  gains `pass_date` as its trailing column. The scientific identity is still
  `(field_id, scene_id, index_name, geometry_version, formula_version)`: `pass_date` is derived
  from `scene_metadata.sensing_datetime`, which is immutable once ingested, so one scene has
  exactly one date and the wider constraint admits nothing the old one rejected. This
  functional dependency is the load-bearing assumption; it holds because the scene row is
  immutable and `pass_date` is always written from it.
- **Index consolidation.** The query inventory (every `Analysis` reference in the tree):
  upsert + re-select (identity columns), per-field timeseries and scenes panel
  (`field_id [+ index_name]`, order `pass_date`), as-of resolution (`field_id + index_name +
  geometry_version + clear floor`, date-bounded, limit 1 each side), audit (`field_id`),
  farm analytics + publish payload (join through Field on `farm_id`, filter `index_name`,
  bound `pass_date`), interpret grounding (`field_id + scene_id + geometry_version`), pipeline
  dedup (`field_id + geometry_version`), retention (full scan where `cog_uri IS NOT NULL`).
  Nothing filters by `scene_id` alone; nothing looks up bare `id` except retention, which holds
  the pass_date. So: one composite `ix_analysis_field_index_date (field_id, index_name,
  pass_date)` replaces all four single-column indexes. `field_id` alone is its prefix;
  `pass_date` alone is the partition key; `index_name` never stands alone; `scene_id` keeps the
  FK but no index (scene_metadata rows are never deleted, so there is no reverse scan to serve).

## Who creates partitions

Three owners, no gaps:

1. **Migration 0008** seeds monthly partitions over [oldest stored pass, today + 3 months]
   plus the `analysis_default` DEFAULT catch-all.
2. **`maintenance.ensure_analysis_partitions`** (weekly beat, Sun 02:30 UTC, deliberately ahead
   of the 03:00 prune) keeps the window rolling: the pure planner in
   `services/worker/partitions.py` names every month from one slack month behind the backfill
   horizon (the horizon floor moves day by day) to a 3-month lookahead, reusing
   `planning.backfill_window` so the partition window and the advertised history depth cannot
   drift. Each missing month is CREATEd inside its own savepoint.
3. **The model itself** (`after_create` hook) creates `analysis_default` for environments stood
   up by `Base.metadata.create_all`, i.e. the DB-gated tests, which know nothing of alembic.

DEFAULT-partition semantics: a row outside every monthly partition lands in `analysis_default`
and stays fully queryable; it is correct, merely unpartitioned. The flip side: a month whose
range already has rows in DEFAULT cannot be created (Postgres would have to move them), so the
upkeep task reports it `skipped` and carries on. This happens only when config widens
`RS_BACKFILL_MONTHS` after rows already aged into DEFAULT, and it self-resolves for all future
months.

## Casualties and how they were handled

- **`RETURNING (xmax = 0)` died.** Postgres refuses system columns in RETURNING through a
  partitioned parent (`cannot retrieve a system column in this context`). The upsert's
  created-vs-refreshed signal is now `(created_at = now())`: `created_at` is written only by
  the insert default and the refresh SET list never touches it, so equality with the
  transaction timestamp marks a fresh row. Caveat (documented in code): re-upserting an
  identity inside the very transaction that created it would also report True; the pipeline
  writes each identity once per run in its own transaction.
- **`pass_date` left `_ANALYSIS_MUTABLE`.** It now sits in the arbiter constraint, so the
  conflict only fires when the stored value already matches, and an ON CONFLICT update may
  never move a row across partitions anyway.
- **`session.get(Analysis, id)` became `session.get(Analysis, (id, pass_date))`** in
  retention; the composite also routes the lookup straight to one partition.

## Migration mechanics (gotchas worth keeping)

A partitioned table cannot be converted in place: 0008 renames `analysis` to `analysis_flat`,
creates the partitioned successor, copies with an explicit column list, drops the flat table,
then builds the composite index (after the copy, one pass). Two naming traps:

- Index names are schema-global. The flat table's PK/unique/secondary indexes must be dropped
  (not just the table renamed) before the successor can reuse `analysis_pkey`,
  `uq_analysis_identity`.
- FK names are per-table, but Postgres's auto-namer avoids any name present in the namespace:
  while `analysis_flat` still held `analysis_field_id_fkey`, the new table's auto-named FK
  came out `analysis_field_id_fkey1`. Both migrations name FKs explicitly and rename to the
  canonical names at the end, so migrated and `create_all` databases agree on every name.

The downgrade is a full inverse (flat rebuild under temporary names, copy back, drop the
partitioned tree, rename into place, recreate the four original indexes).

**Rehearsal method** (worth repeating for any future table rebuild): scratch DB
`remote_sense_mig`, `alembic upgrade <pre-revision>`, seed rows spanning years (2019/2025/2026
exercised the dynamic month window: 92 partitions), `alembic upgrade head`, assert
`tableoid::regclass` routing + `pg_constraint` names, `alembic downgrade -1`, assert the flat
original (relkind, names, indexes), `alembic upgrade head` again. The compose `migrate` service
applies 0008 to the dev DB on the next stack start.

## Test surface

- `tests/test_partitions.py` (8, pure): month math, window span/contiguity, validation.
- `tests/test_partitions_db.py` (4, DB-gated): create_all routes inserts to DEFAULT; ensure
  creates exactly the missing months then reports them present (idempotent); rows route to
  their month and an out-of-window row to DEFAULT; an occupied-DEFAULT month is skipped, not
  fatal, and its rows stay queryable.
- `tests/test_repositories.py` updated: the RETURNING idiom assertion and `pass_date` excluded
  from the mutable set.
- The existing DB suites (analysis upsert, retention, tasks, workspace, publish) now run
  against the partitioned table via the DEFAULT partition, which proves ON CONFLICT ON
  CONSTRAINT and the whole read surface against PG16 partitioning for free.

A test-seeding gotcha for the archive: without a `relationship()` between two mappers,
SQLAlchemy's unit of work does not order their INSERTs by FK; seed the `scene_metadata` row
and `flush()` before adding the `Analysis` row.
